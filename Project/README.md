# Проектная работа

## Тема: Отказоустойчивая мультисайтовая фабрика EVPN-VXLAN для игровых сервисов с изолированной тестовой средой

> «Цель нашей Anycast-маршрутизации — сделать так, чтобы школьник из Красноярска попал в дата-центр Франкфурта с пингом 300, мгновенно умер в первом раунде и пошел делать уроки, а не нагружал нам фабрику своим UDP-флудом.»

### Цели

1. Построить два независимых сайта (RU и EU) на EVPN-VXLAN с отказоустойчивым подключением хостов (ESI all-active).
2. Обеспечить вход игрока через anycast и закрепление сессии через unicast VIP, с переключением на второй сайт при отказе сервиса или сайта.
3. Связать сайты только через эмуляцию Интернета (кольцо из четырёх ISP-узлов), без DCI. 
4. Выделить тестовую среду в отдельный VRF с полной изоляцией от игровой и доступом извне только через jump host.
5. Проверить отказоустойчивость при отказе сервиса, Leaf, Spine, ISP и сайта.
6. Зафиксировать отличия лабораторной модели от реального production и обосновать каждое проектное решение.

## 1. О проекте

Лабораторная модель мультисайтовой фабрики для высоконагруженных игровых сервисов. Два независимых сайта, RU и EU, связаны только через эмуляцию Интернета: общего L2-домена и выделенных каналов между ними нет.

Игрок входит по anycast в ближайший сайт. Сессия закрепляется за сайтом через unicast VIP. При отказе сервиса или всего сайта VIP снимается, и игрок уходит на второй сайт. На каждом сайте есть изолированная тестовая среда (VRF TEST), доступная из Интернета только через jump host.

### 5.1 Топология и фабрика сайта

Для каждого из сайтов (RU и EU) принята классическая двухуровневая Clos-топология (Spine-Leaf). Spine-коммутаторы выполняют роль исключительно высокопроизводительного Underlay-транзита IPv4/IPv6 и не участвуют в терминации VXLAN-туннелей (не содержат Tenant VRF), а также функционируют как EVPN Route Servers. Leaf-коммутаторы совмещают функции Anycast Gateway (AGW) для хостов и Border Gateway (BGW) для внешних стыков.

| Вариант архитектуры                                  | Критерии сравнения и техническое обоснование | Статус     |
| ---------------------------------------------------- | --- | ---------- |
| **Двухуровневая Clos (Spine-Leaf, 2+2 на сайт)**     | **Преимущества:** Обеспечивает предсказуемую горизонтальную масштабируемость, минимизирует задержки (равное число хопов между любыми хостами фабрики). Позволяет эффективно распределять трафик с помощью ECMP.<br>**Контроль отказов:** Изолирует сбои на уровне одного линка или узла. При выходе из строя одного Spine пропускная способность фабрики снижается ровно на 50% без потери связности. | **Выбран** |
| **Collapsed Core (Одноуровневая фабрика)**           | **Технические ограничения:** Отсутствие выделенного уровня распределения исключает возможность горизонтального масштабирования (Scale-Out).<br>**Риски:** Ограниченная плотность портов. Любая авария на одном из Core-узлов приводит к деградации всей инфраструктуры и повышает риск разделения сети (Split-Brain) в кластерных решениях. | *Отклонён* |
| **Выделенные Border Leaf для стыка с ISP**           | **Преимущества:** Чёткое разделение ролей (Separation of Concerns), изоляция публичного и приватного периметров.<br>**Причина отклонения:** Повышает аппаратную избыточность и стоимость решения на начальном этапе. Совмещение ролей AGW и BGW на текущих Leaf полностью закрывает потребности по производительности в рамках лабораторной модели. | *Отклонён* |
| **Трехуровневая фабрика (Spine, Super-Spine, Leaf)** | **Область применения:** Избыточна для масштаба данной сети (2 Leaf на сайт).<br>**Недостатки:** Увеличивает задержку распространения пакетов (propagation delay) из-за дополнительных хопов и усложняет траблшутинг BGP EVPN Overlay. | *Отклонён* |

### 5.2 Архитектура Underlay-сети

Underlay-сеть построена на базе протокола eBGP с использованием концепции IPv6 Link-Local Peerings (BGP Unnumbered, RFC 5549 / RFC 8950). Межкоммутационные IPv4-адреса полностью отсутствуют. Передача IPv4 NLRI осуществляется с использованием IPv6 Next-Hop. На всех интерфейсах фабрики жестко зафиксировано значение MTU 9000 для исключения фрагментации VXLAN-пакетов.

| Вариант реализации                               | Технико-экономический анализ | Статус     |
| ------------------------------------------------ | --- | ---------- |
| **eBGP IPv6 Link-Local (BGP Unnumbered)**        | **Обоснование:** Исключает необходимость разработки, поддержки и распределения IPv4-плана адресации для линков (`/31` или `/30`), сводя к нулю человеческий фактор при настройке интерконнектов.<br>**Управление:** Вся фабрика функционирует на базе одного протокола (BGP), что упрощает конвергенцию. Конфигурация интерфейсов становится полностью стандартизированной и шаблонной. | **Выбран** |
| **IGP (OSPF / IS-IS) + iBGP EVPN**               | **Недостатки:** Требует запуска и поддержки двух разнородных протоколов маршрутизации. Повышает нагрузку на CPU управляющего процессора (Control Plane) коммутаторов.<br>**Масштабируемость:** При росте фабрики усложняется поддержка зон OSPF / уровней IS-IS и конфигурация Route Reflectors для iBGP. | *Отклонён* |
| **eBGP IPv4 Numbered (выделение `/31` на линк)** | **Недостатки:** Высокие административные расходы на управление адресным пространством IPv4. Риск возникновения асимметрии маршрутизации или прерывания связности из-за ошибок дублирования IP-адресов при ручной конфигурации. | *Отклонён* |

### 5.3 Архитектура Overlay-сети

Маршрутизация между виртуальными сетями реализована по схеме симметричного IRB (Symmetric IRB). Для каждого VRF (GAME и TEST) выделен уникальный транзитный L3VNI (10066 и 10077 соответственно). Обмен MAC- и IP-адресами хостов осуществляется через eBGP EVPN-сессии между Loopback0-интерфейсами Leaf и Spine-маршрутизаторами (Multihop). На Spine включена функция `next-hop-unchanged`.

| Вариант реализации                        | Влияние на Control Plane и Data Plane | Статус     |
| ----------------------------------------- | --- | ---------- |
| **Symmetric IRB (L3VNI на каждый VRF)**   | **Обоснование:** Оптимальное масштабирование таблиц маршрутизации. Коммутаторам Leaf не требуется хранить MAC-адреса и ARP-записи хостов из удаленных сегментов (VTEP), если на них нет локальных потребителей этих сетей.<br>**Маршрутизация:** Маршрутизация и коммутация происходит в транзитном L3VNI, что снижает нагрузку на фабрику. | **Выбран** |
| **Asymmetric IRB**                        | **Недостатки:** Требует присутствия абсолютно всех Layer 2 VNI (и соответствующих VLAN) на каждом Leaf-коммутаторе фабрики.<br>**Риски:** Лавинообразный рост таблиц MAC-адресов и ARP-кэша на всех узлах. Непригодно для многопользовательских динамических сред из-за неэффективного расхода аппаратной памяти (TCAM). | *Отклонён* |
| **iBGP EVPN (Единая автономная система)** | **Недостатки:** В рамках eBGP Underlay требует построения сложной иерархии автономных систем или внедрения костылей маршрутизации. Усложняет изоляцию сайтов, так как автоматическое распределение Route Targets (Auto-RT) в рамках одной AS размывает границы доменов отказов. | *Отклонён* |

### 5.4 Подключение хостов

Высоконагруженные хосты (игровые серверы) подключены одновременно к двум Leaf-коммутаторам в режиме EVPN ESI All-Active. Агрегирование каналов обеспечивается стандартным протоколом LACP (IEEE 802.1AX). На стороне Leaf-коммутаторов настраивается идентичный Ethernet Segment Identifier (ESI) и единый статический LACP System ID.

| Технология мультихоминга           | Сравнительный анализ надежности и стандартизации | Статус     |
| ---------------------------------- | --- | ---------- |
| **EVPN ESI All-Active (RFC 7432)** | **Обоснование:** Открытый, вендоронезависимый стандарт. Не требует организации выделенного физического межкоммутаторного линка связи (Peer-Link).<br>**Отказоустойчивость:** Обеспечивает балансировку трафика на базе потоков (Flow-based) по обоим линкам. Механизмы Split-Horizon и Designated Forwarder (DF) предотвращают образование петель на уровне плоскости управления EVPN. | **Выбран** |
| **Вендорский MC-LAG / MLAG**       | **Недостатки:** Закрытая проприетарная технология, жестко привязывающая дизайн к одному производителю.<br>**Риски:** Требует выделения дорогостоящих портов под Peer-Link. Сбой в работе Peer-Link или рассогласование State Machine часто приводит к полной изоляции хоста или образованию L2-петель. | *Отклонён* |
| **Single-Homed (одиночные линки)** | **Технический дефект:** Наличие единой точки отказа (SPOF) в виде одного интерфейса или одного Leaf-коммутатора, что недопустимо для архитектуры Tier-1/Tier-2 игровых сервисов. | *Отклонён* |

### 5.5 Архитектура игрового сервиса (VRF GAME)

Игровой сервис развернут внутри выделенного `VRF GAME` (VLAN 666, L2VNI 10666, L3VNI 10066). Серверы (vEOS) анонсируют свои VIP-адреса (Anycast VIP `10.0.100.100/32` и локальный Unicast VIP) по протоколу eBGP непосредственно на Leaf-коммутаторы. Сессии строятся через SVI-интерфейсы. На Leaf-коммутаторах настроены жесткие входящие prefix-list, разрешающие прием только точных маршрутов `/32`.

[Игрок] &rarr; [Интернет (Anycast 10.0.100.100/32)] &rarr; [Ближайший Site BGW] &rarr; [Закрепление Unicast VIP]

| Механизм                       | Описание |
| ------------------------------ | --- |
| Механизм Anycast-входа         | Позволяет минимизировать сетевую задержку (RTT) за счет автоматического направления пакетов игрока на географически ближайший сайт силами глобальной BGP-маршрутизации Интернета. |
| Механизм Unicast-закрепления   | Так как Anycast не гарантирует стабильность пути при изменении топологии Интернета (что критично для stateful UDP-сессий игрового движка), первичная авторизация переводит клиента на выделенный Unicast VIP конкретного дата-центра. |
| Механизм сходимости (Failover) | При падении игрового демона на сервере, BGP-сессия Host-Leaf разрывается. Leaf мгновенно генерирует BGP Withdraw. Маршрут отзывается из глобального Интернета, и новые игроки автоматически перенаправляются на резервный сайт. |

### 5.6 Инфраструктура стыка с операторами

Каждый Leaf-коммутатор имеет независимые routed-аплинки к двум провайдерам: ISP1 (основной) и ISP2 (резервный). Взаимодействие строится по eBGP с использованием выделенного диапазона CGNAT (RFC 6598) `100.64.0.0/10` на стыках. Для минимизации флуктуаций задержки (Jitter) распределение трафика в режиме ECMP между разными провайдерами преднамеренно исключено.

| Схема аплинков                                                  | Технико-экономическое обоснование | Статус     |
| --------------------------------------------------------------- | --- | ---------- |
| **Dual-Homed (Active/Standby via BGP Local-Pref & AS-Prepend)** | **Обоснование:** Трафик жестко направляется через основного провайдера (ISP1 с `Local-Pref 200`). Второй провайдер используется как "холодный" резерв (`Local-Pref 100`, анонсы наружу идут с AS-Prepend).<br>**Преимущество:** Гарантирует стабильный пинг для игроков без постоянных переключений между трассами разных операторов. | **Выбран** |
| **Dual-Homed с балансировкой (ECMP)**                           | **Риски:** Провайдеры имеют разные точки обмена трафиком и аплинки. Балансировка пакетов одной игровой сессии через два разных ISP приведет к постоянному изменению задержки (Jitter) и возможной внеочередной доставке пакетов (Out-of-Order packets), что ломает сетевой код игры. | *Отклонён* |
| **Single-Homed (Один ISP на сайт)**                             | **Критический дефект:** Полное отсутствие отказоустойчивости на уровне оператора связи. Любые регламентные работы или авария на оптической магистрали провайдера полностью изолируют игровой сайт. | *Отклонён* |

### 5.7 Архитектура и изоляция тестовой среды (Лабораторное допущение)

Тестовая среда функционирует в рамках выделенного Layer 3 контекста маршрутизации (`VRF TEST`, VLAN 777, L2VNI 10777, L3VNI 10077). Архитектура обеспечивает абсолютную изоляцию тестового контура от продуктового игрового сегмента (`VRF GAME`) на L2/L3 (VLAN, VNI, VRF) уровнях модели OSI для исключения взаимного влияния и предотвращения утечки конфиденциальных данных.

### 5.8 Организация удаленного доступа и Jump Host (Лабораторное допущение)

Для обеспечения контролируемого административного доступа разработчиков из внешней сети к изолированным тестовым хостам внедрена подсистема транзитного узла (Jump Host). В рамках ресурсных ограничений лабораторной модели EVE-NG принято допущение: роль Jump Host выполняет выделенный интерфейс `Loopback10` коммутатора `Leaf1` текущего сайта, функционирующий внутри `VRF TEST`.

**Логика прохождения трафика и программирования FIB:**

| Вектор                                                          | Шаг | Описание |
| --------------------------------------------------------------- | --- | --- |
| Входящий вектор (Ingress Path)                                  | 1   | Внешний разработчик инициирует SSH-сессию на публичный IP-адрес интерфейса `Loopback10` соответствующего региона (`10.0.78.10/32` для RU, `10.0.178.10/32` для EU). |
| Входящий вектор (Ingress Path)                                  | 2   | Пакет поступает от узла `ISP2` на интерфейс `Leaf2` (Eth5). Маршрутизатор `Leaf2` не имеет локального интерфейса в этой подсети, но обладает BGP EVPN Type-5 маршрутом, полученным от `Leaf1`. |
| Входящий вектор (Ingress Path)                                  | 3   | `Leaf2` выполняет инкапсуляцию пакета в VXLAN-заголовок с транзитным `L3VNI 10077` и отправляет его через Underlay-сеть в сторону `Leaf1` (Next-Hop: `Loopback1` VTEP-адрес коммутатора `Leaf1`). |
| Входящий вектор (Ingress Path)                                  | 4   | `Leaf1` терминирует VXLAN-туннель, декапсулирует пакет и передает его на локальный демон SSH, предварительно активированный в данном VRF (`management ssh vrf TEST`). |
| Исходящий вектор (Egress Path) и защита от On-Link зацикливания | 1   | Адресация интерфейсов `Loopback10` специально вынесена за пределы продуктовых тестовых подсетей хостов (`10.0.77.0/24` и `10.0.177.0/24`). |
| Исходящий вектор (Egress Path) и защита от On-Link зацикливания | 2   | Благодаря этому тестовый хост при получении пакетов от Jump Host или при ответе на них не считает данный адрес находящимся в локальном L2-сегменте (not on-link). Трафик гарантированно отправляется на Anycast Gateway фабрики (`10.0.77.1` / `10.0.177.1`), обеспечивая симметричность маршрутизации. |

**Политики безопасности и фильтрации на периметре TEST:**

| Политика                                 | Описание |
| ---------------------------------------- | --- |
| Ограничение платформы (Eth5 Leaf2)       | Интерфейсный ACL (`ip access-group ... in/out`) на `Ethernet5` Leaf2 на vEOS-lab не поддерживается: CLI возвращает `not supported on this hardware platform`. Фильтрация транзитного трафика из Интернета на стыке с ISP2 в лабораторной модели невозможна. В production эту функцию выполняет входящий ACL на Border Leaf или внешний межсетевой экран (см. раздел 8). |
| Фильтрация маршрутов на стыке ISP2       | Из ISP2 в VRF TEST принимается только `0.0.0.0/0` (`RM-TEST-IN`), наружу анонсируется только `10.0.78.10/32` (`RM-TEST-OUT`, `PL-LO10`) для RU и `10.0.178.10/32` для EU. У ISP нет маршрутов к TEST-подсетям `10.0.77.0/24` и `10.0.177.0/24`, поэтому прямой доступ из Интернета к тестовым хостам невозможен (проверка T2). |
| Динамические ACL платформы               | На Leaf2 присутствуют только динамические списки `$$arbgp-ttlSec-ip-vrf-TEST$$` (защита BGP-сессии с ISP2 по TTL) и `default-control-plane-acl`. Они создаются платформой автоматически, к `Ethernet5` не привязаны и не являются элементом дизайна проекта. |
| Исходящий доступ из тестовой среды       | Исходящий доступ тестовых хостов в Интернет ограничен отсутствием обратных маршрутов: ISP2 не знает TEST-подсетей, а `Host-RU` и `Host-EU` получают ответы только от своих шлюзов (проверка T5). Явный запрет на Anycast-шлюзах фабрики в лабораторной модели не настроен. |

**Дополнительная защита Control Plane и SSH (не применяется в лаборатории):**

В каталогах `Configs/RU/` и `Configs/EU/` приведены ACL для защиты Control Plane и SSH management в VRF TEST. Они сохранены как справочный вариант и в работающие конфигурации устройств не загружались, поэтому в проверках раздела 6 не участвуют.

| Устройство        | ACL                                                    | Назначение |
| ----------------- | ------------------------------------------------------ | --- |
| Leaf1 RU / EU     | `ACL-SSH-JUMP` в `management ssh` (VRF TEST)            | Разрешает SSH к Lo10 только из подсетей клиентов `198.51.100.0/24` и `203.0.113.0/24`, остальное `deny ip any any log` |
| Leaf1 RU / EU     | `ACL-CP-TEST` в `system control-plane` (VRF TEST)       | Разрешает SSH и ICMP к Lo10 из клиентских подсетей, трафик подсети TEST и отслеживаемые сессии. Остальное `deny ip any any log` |
| Leaf2 RU / EU     | `ACL-CP-TEST` в `system control-plane` (VRF TEST)       | Защита CPU Leaf2: разрешает BGP, BFD и ICMP с ISP2 (`100.64.102.0` для RU, `100.64.112.0` для EU) и трафик подсети TEST. Остальное `deny ip any any log` |

Эти ACL защищают только плоскость управления коммутатора (SSH, BGP, BFD, ICMP на самом устройстве) и не фильтруют транзитный трафик между ISP2 и тестовым контуром. Их применимость на vEOS-lab не проверялась, поэтому они не отражены в проверках T1–T7.

### 5.9 Архитектура подключения пользователей и балансировка игрового сервиса

Для минимизации сетевых задержек (RTT), исключения влияния нестабильности трасс Интернета на активные игровые сессии и обеспечения бесшовного восстановления после сбоев (Failover) реализована гибридная Anycast/Unicast-архитектура доставки сервиса.

| Компонент архитектуры                | Механизм реализации и системная логика |
| ------------------------------------ | --- |
| **Точка входа (Anycast VIP)**        | На Loopback100-интерфейсах игровых хостов обоих сайтов (RU и EU) назначен идентичный IP-адрес `10.0.100.100/32`. Данный префикс анонсируется по eBGP от хостов к Leaf-коммутаторам, а затем транслируется в Интернет-кольцо. Глобальная BGP-маршрутизация автоматически направляет пакеты игрока к географически ближайшему дата-центру по кратчайшему пути AS-Path. |
| **Закрепление сессии (Unicast VIP)** | Протокол UDP, применяемый в игровых движках, чувствителен к изменению маршрута: смена VTEP или BGW в процессе игры разорвет stateful-сессию. Для исключения этого Anycast VIP используется **исключительно для первичного входа** (авторизация, получение листинга серверов). При установлении постоянной игровой сессии клиент перенаправляется на уникальный Unicast VIP конкретного сайта (`10.0.100.1/32` для RU или `10.0.100.2/32` для EU), жестко зафиксированный за локальным хостом. |
| **Сходимость при отказе сервиса**    | В случае падения игрового приложения или планового вывода сервера из эксплуатации, демон маршрутизации на хосте гасит интерфейс Loopback100/101. eBGP-сессия Host-Leaf генерирует мгновенный отзыв маршрута (BGP Withdraw). Маршрут Anycast и локальный Unicast VIP исчезают из таблиц фабрики и внешних ISP. Сеть общего пользования перестраивается, и новые запросы игроков мгновенно уходят на резервный сайт. |
| **Защита от межсайтового L2-шторма** | Поскольку Anycast-адрес присутствует на обоих сайтах, прямая организация сквозного Data Center Interconnect (DCI) на Layer 2 привела бы к катастрофическому зацикливанию трафика и BUM-штормам. В текущей архитектуре сайты связаны **строго через L3-маршрутизацию** эмулируемого Интернета. EVPN Type-2 (MAC/IP) и Type-3 (IMET) маршруты принципиально не покидают пределов своего сайта, полностью изолируя широковещательные домены. |

### 5.10 Интернет (Лабораторное допущение)

Взаимодействие между независимыми фабриками сайтов RU и EU организовано без использования выделенных каналов Data Center Interconnect (DCI) или сквозных Layer 2 туннелей. Связность обеспечивается исключительно через распределенную транзитную инфраструктуру, эмулирующую глобальную сеть Интернет.

| Элемент                                      | Описание |
| -------------------------------------------- | --- |
| Четырехузловое ядро (4-node Core Ring)       | Магистраль Интернета сформирована четырьмя независимыми узлами операторов связи (`ISP1-RU`, `ISP2-RU`, `ISP1-EU`, `ISP2-EU`), замкнутыми в отказоустойчивое кольцо через стыки `/31` (сеть `192.0.2.0/24`). Каждая автономная система (AS) представляет собой отдельный домен маршрутизации. |
| Протокол взаимодействия                      | Внутри транзитного кольца используется исключительно протокол внешнего динамического хоуминга (eBGP). Внутренние протоколы IGP (OSPF/IS-IS) и iBGP-сессии преднамеренно исключены. Сетевая связность обеспечивается классической хмелевой маршрутизацией (Hop-by-Hop) на базе глобальных таблиц IPv4 RIB. |
| Изоляция плоскости Overlay (VXLAN Bordering) | Транзитная сеть оперирует только стандартными IPv4-префиксами. EVPN-анонсы фабрик (Type-2, Type-3, Type-5) жестко терминируются на Leaf-коммутаторах (BGW) и принципиально не передаются в сторону ISP. Межсайтовый трафик проходит через Интернет в открытом, декапсулированном виде. |

**Политики прохождения трафика и маршрутные карты:**

| Режим                                        | Описание |
| -------------------------------------------- | --- |
| Штатный режим (Primary Path)                 | По умолчанию межсайтовый трафик продуктивного контура (`VRF GAME`) направляется по кратчайшему пути через Tier-1 операторов первого уровня: `BGW-RU` &rarr; `ISP1-RU` &rarr; `ISP1-EU` &rarr; `BGW-EU`. |
| Нештатный режим (Path Hunting & Convergence) | При аварии на магистральном линке между `ISP1-RU` и `ISP1-EU` (интерфейсы `Eth4`), протокол eBGP запускает процедуру перерасчета путей. Трафик автоматически перенаправляется по длинному плечу кольца через транзитные узлы вторых провайдеров (`ISP2-RU` и `ISP2-EU`), добавляя в цепочку маршрутизации один дополнительный хоп (AS-Hop), но сохраняя полную доступность сервисов. |

## 7. Риски и допущения

В данном разделе зафиксированы ключевые допущения лабораторной модели, а также фундаментальные архитектурные риски, присущие текущей схеме построения сети. Анализ разделен на ограничения, вызванные спецификой среды эмуляции, и скрытые уязвимости в дизайне самой фабрики.

### 7.1 Допущения лабораторной модели стенда

Данные пункты являются сознательным компромиссом для реализации проекта в среде виртуализации EVE-NG и требуют полной перестройки инфраструктуры при переходе к промышленной эксплуатации.

| Пункт                                                                                            | Суть допущения | Проблема |
| ------------------------------------------------------------------------------------------------ | --- | --- |
| Угроза дестабилизации Control Plane при совмещении роли коммутатора и Jump Host                  | Терминация входящих SSH-сессий разработчиков в `VRF TEST` выполняется непосредственно на управляющем интерфейсе (`Loopback10`) коммутатора ядра фабрики `Leaf1`. | Коммутатор вынужден тратить ресурсы своего главного процессора (Control Plane CPU) на обработку прикладного трафика. В реальной инфраструктуре это категорически недопустимо, так как открывает прямой вектор для DoS/DDoS-атак на сетевое устройство (например, через Brute-Force или уязвимости в SSH-стеке). Перегрузка CPU приведет к падению BGP Underlay/Overlay сессий всего сайта и отказу продуктивного сегмента игры. |
| Зависимость административного доступа от стабильности Overlay-фабрики (Совмещение ролей AGW/BGW) | Из-за совмещения ролей пограничного шлюза (BGW) и шлюза хостов (AGW) на одном комплекте коммутаторов трафик разработчика поступает на `Leaf2` (Eth5), инкапсулируется в VXLAN-туннель с транзитным `L3VNI 10077` и отправляется на `Leaf1` через Underlay-сеть фабрики. | Доступ к Jump Host для управления и диагностики тестовой среды напрямую зависит от работоспособности внутренних туннелей фабрики. При аварии внутренних линков Spine-Leaf или сбое в работе EVPN Control Plane сессия администратора разорвется, даже если сам тестовый хост и интерфейс подключения к ISP функционируют штатно. В production-архитектурах внешние стыки и Bastion-серверы выносятся за пределы внутренней VXLAN-фабрики. |
| Отсутствие прикладного L7 Health-Checking (Эмуляция сервиса на сетевой ОС)                       | Роль игрового сервера выполняет экземпляр vEOS-lab, а отзыв Anycast/Unicast VIP-адресов завязан исключительно на ручное изменение административного состояния интерфейса Loopback (`shutdown`). Реальный мониторинг доступности игрового демона на прикладном уровне (L7) в схеме отсутствует. | В случае зависания игрового процесса, падения базы данных или переполнения пула соединений при сохранении физического линка eBGP-сессия Host-Leaf останется активной. Фабрика и Интернет-кольцо продолжат направлять трафик игроков на неработающий сервер («черная дыра» для трафика), что полностью нивелирует отказоустойчивость Anycast. |
| Анонсирование маршрутов `/32` (Host Routes) в эмулируемый Интернет                               | Игровые Anycast/Unicast VIP-адреса, а также адрес Jump Host передаются в транзитное кольцо провайдеров в виде точных префиксов с маской `/32`. | Архитектура работоспособна только внутри изолированного лабораторного стенда. В реальной сети Интернет (глобальная таблица маршрутизации BGP Full-View) операторы Tier-1/Tier-2 жестко фильтруют любые анонсы длиннее `/24` (RFC 7454). Для работы в Production потребуется выделение полноценного блока адресов и переработка схемы балансировки. |
| Упрощенная топология транзитной сети (Проблема Path Hunting)                                     | Модель Интернета представлена четырьмя eBGP-узлами без использования политик предотвращения петель на базе сообществ (BGP Communities). | При аварии на магистральных линках кольца (например, стык ISP1-RU — ISP1-EU) протокол eBGP запускает процедуру последовательного перебора альтернативных маршрутов (Path Hunting). В процессе сходимости трафик между сайтами может временно зацикливаться, приводя к потере пакетов и лавинообразному росту задержек (RTT). |

### 7.2 Системные архитектурные риски дизайна фабрики

Данные риски заложены в саму логику спроектированного решения и в равной степени проявляются как на виртуальных экземплярах, так и на реальном аппаратном оборудовании (ASIC) при промышленной эксплуатации.

| Пункт                                                                                       | Проблема | Риск |
| ------------------------------------------------------------------------------------------- | --- | --- |
| Разделение плоскости управления и риск Split-Brain поверх ESI All-Active                    | Игровой сервер подключен к Leaf-1 и Leaf-2 через Port-Channel в режиме EVPN ESI All-Active и строит независимые eBGP-сессии с каждым из них. При этом между самими коммутаторами Leaf отсутствует выделенный логический или физический межкоммутаторный линк связи (Peer-Link / MLAG-интерконнект), и они функционируют в разных автономных системах (ASN). | При локальной деградации Control Plane (например, если один из Leaf перестал корректно обрабатывать или анонсировать BGP EVPN Route Type-1/Type-4 префиксы, но продолжает держать LACP и BGP-сессию с хостом), входящий трафик к Anycast/Unicast VIP-адресам начнет распределяться асимметрично. Это приведет к дропам пакетов на уровне фабрики, разрушению stateful UDP-сессий игрового движка и непредсказуемому поведению механизмов локального отсечения петель (Split-Horizon). |
| Эффект суб-оптимальной маршрутизации при локальных отказах (Downstream/Upstream Tromboning) | Из-за отсутствия прямой физической связности между Leaf-1 и Leaf-2 внутри сайта, любой транзит трафика между ними возможен только через уровень Spine-коммутаторов. | В случае падения линка между `Host-RU` и `Leaf1-RU` (например, выдернут кабель Eth1 на хосте), `Leaf1-RU` продолжит получать входящий трафик для этого хоста из внешней сети (так как BGP-сессия с ISP1 активна). Не имея локального порта в сторону хоста, `Leaf1-RU` будет вынужден инкапсулировать этот трафик в VXLAN и отправлять его на Spine, чтобы тот доставил пакет на `Leaf2-RU`. Данный эффект («трамбование» трафика через Spine) удваивает задержку (RTT) внутри дата-центра, непредсказуемо утилизирует полосу аплинков фабрики и критически увеличивает Jitter для игроков. |
| Масштабируемость eBGP-сессий Host-to-Leaf и риски исчерпания ресурсов TCAM                  | Архитектурный дизайн предполагает запуск eBGP-сессии непосредственно между каждым игровым сервером и парой Leaf-коммутаторов фабрики. | При горизонтальном масштабировании игрового кластера (Scale-Out до сотен физических или виртуальных серверов на сайт) нагрузка на Control Plane Leaf-коммутаторов возрастает лавинообразно. Необходимость поддержания огромного количества BGP-соседств и обработка постоянных BGP Keepalive/Update сообщений может вызвать перегрузку процессора коммутатора. Более того, ручное назначение RD/RT для каждой хостовой сессии и генерация EVPN Type-5 маршрутов на каждый `/32` префикс грозит исчерпанием аппаратных таблиц TCAM (Routing Table/L3 FIB) на Leaf, что приведет к переходу коммутаторов в режим программной маршрутизации пакетов (Software Forwarding) и катастрофическому падению производительности сети. |


## 8. Реальный production

Лабораторный стенд верифицирует базовую математическую и логическую корректность Control Plane (EVPN/eBGP), но принципиально не отражает эксплуатационные, масштабируемые и защитные свойства реальной инфраструктуры. В данном разделе представлен детальный технический анализ трансформации лабораторной модели в отказоустойчивую архитектуру промышленного класса (Production Tier-1) с учетом геополитической и инфраструктурной специфики регионов RU и EU в 2026 году.

### 8.2 Инженерная реализация и устранение лабораторных допущений

#### 1. Выделенная геораспределенная Edge-архитектура и безопасность административного доступа

В промышленной эксплуатации терминация входящих сессий разработчиков на Control Plane процессорах коммутаторов фабрики категорически запрещена. Административный доступ разделен в соответствии с требованиями регуляторов каждого региона.

| Аспект                   | Описание |
| ------------------------ | --- |
| Реализация в RU-сегменте | Внешний стык тестовой среды `VRF TEST` на Border Leaf подключается через сертифицированный криптошлюз (ГОСТ VPN). В качестве Jump Host используется катастрофоустойчивый кластер виртуальных машин (Bastion), развернутый за аппаратным межсетевым экраном (например, UserGate/Код Безопасности). Авторизация инженеров завязана на корпоративный каталог (ALD Pro / Active Directory) с обязательным применением второго фактора (MFA via SMS/OTP) и тотальной записью SSH-сессий (PAM-системы). |
| Реализация в EU-сегменте | Доступ инженеров организуется по модели **ZTNA (Zero Trust Network Access)**. Трафик разработчиков терминируется на шлюзах доступа в DMZ, контролируемых NGFW Fortinet/Palo Alto. Идентификация пользователей интегрирована со сквозной SSO-платформой (Okta / Azure AD) с контекстной проверкой состояния устройства (Device Health Check) на соответствие стандартам безопасности ISO 27001 и GDPR. |

#### 2. Промышленная интеграция Anycast и L7 Health-Checking на хостах

Вместо ручного управления интерфейсами Loopback на коммутаторах Arista, в реальной сети используется динамический прикладной Health-Checking.

| Аспект                         | Описание |
| ------------------------------ | --- |
| Решение                        | На игровых серверах (Bare-Metal ноды под управлением Linux) разворачивается отказоустойчивый стек **BIRD2 + Keepalived**. Серверы строят eBGP-сессии с парой Service Leaf-коммутаторов своей ESI-группы. На Leaf активируется механизм `bgp listen range`, избавляющий от необходимости вручную прописывать сотни хостовых BGP-сессий. |
| Механизм сходимости (Failover) | Локальный демон на сервере непрерывно опрашивает сокет игрового процесса на Layer 7 (UDP/TCP порт игры). Если игровой сервер зависает, переполняется по CPU или теряет связь с базой данных, скрипт мгновенно отправляет сигнал `SIGKILL` процессу BIRD или опускает вес маршрута. eBGP-сессия Host-Leaf инициирует отзыв префикса (`BGP Withdraw`). Благодаря активированному на линках **BFD (Bidirectional Forwarding Detection)** с таймерами `100ms * 3`, неработающий сервер исключается из Anycast/Unicast пула фабрики и глобального Интернета менее чем за **300 миллисекунд**, полностью предотвращая появление «черных дыр» для трафика игроков. |

#### 3. Легитимная маршрутизация в глобальной сети Интернет (Уход от префиксов `/32`)

Публичные операторы связи в Internet Full-View производят как правило фильтрацию префиксов длиннее `/24` (RFC 7454 - безопасность BGP). Анонсирование лабораторных `/32` на реальном стыке приведет к немедленному сбросу трафика апстримами.

| Аспект             | Описание |
| ------------------ | --- |
| Решение            | Компания-оператор приобретает у RIR (RIPE NCC) собственную независимую автономную систему (Provider-Independent ASN) и выделяет два независимых блока адресов класса `IPv4 /24` (один для RU, один для EU). |
| Глобальный Anycast | Для Anycast-входа выделяется одна общая подсеть `/24`, которая анонсируется одновременно из московского (М9/MSK-IX) и франкфуртского (Equinix/DE-CIX) узлов связи. Внутри этой сети на хостах настраивается Anycast VIP. Для уникальных Unicast-сессий каждого региона используются свои локальные блоки `/24`. Все анонсы верифицируются созданием цифровых сертификатов **RPKI ROA** в личном кабинете RIPE NCC для предотвращения перехвата трафика (BGP Hijacking) мировыми провайдерами. |

#### 4. Ликвидация эффекта трамбования трафика (Downstream Tromboning)

В Clos-топологиях без Peer-Link локальный отказ одного интерфейса на хосте приводит к неэффективному прохождению пакетов через Spine-уровень фабрики.

| Аспект  | Описание |
| ------- | --- |
| Решение | Поскольку в production-архитектуре роли BGW и AGW жестко разделены, Edge-трафик сначала приходит на выделенные Border Leaf. На Border Leaf активируется технология **EVPN aliasing и mass withdraw (RFC 7432), fast-reroute по ESI**. В случае падения физического линка между `Leaf1` и игровым сервером, `Leaf1` мгновенно узнает об этом по протоколу LACP, но не удаляет маршрут к хосту из своей таблицы. Он начинает прозрачно перенаправлять входящий из Интернета трафик этого хоста на `Leaf2` через выделенный резервный VXLAN-туннель. Это полностью исключает вовлечение Spine-коммутаторов в обработку локальной аварии, минимизирует внутренний Jitter и сохраняет стабильный пинг у конечных игроков. |

#### 5. Транзитная связность и защита от DDoS-атак в условиях санкционного разделения сетей

Прямая связность между RU- и EU-сегментами Интернета в 2026 году характеризуется повышенными задержками и нестабильностью трасс из-за отсутствия прямых стыков у многих европейских Tier-1 операторов с российскими магистралями.

| Аспект                                     | Описание |
| ------------------------------------------ | --- |
| Защита от DDoS в RU-регионе                | Аплинки Border Leaf в России подключаются к отечественным геораспределенным распределителям трафика (**StormWall, QRATOR или DDoS-Guard**). Очистка игрового UDP-флуда и защита от ботнетов происходит на базе L7-анализаторов игровых протоколов, развернутых в точках присутствия внутри РФ. |
| Защита от DDoS в EU-регионе                | Аплинки подключаются к международным лидерам очистки (**Cloudflare Magic Transit или Akamai**). Очищенный трафик доставляется в европейский ЦОД по GRE/IPsec туннелям. |
| Межсайтовый транзит (Синхронизация данных) | Для синхронизации профилей игроков и баз данных между RU и EU сайтами публичный Интернет не используется из-за рисков BGP-блокировок и высоких потерь пакетов. Арендуется выделенный трансграничный Layer 3 VPN канал у нейтрального международного транзитного оператора. На стыках Border Leaf включается аппаратное шифрование. |

> **Примечание по архитектуре:**
> Классический подход к балансировке (использование стандартных реверс-прокси вроде Nginx, HAProxy или облачных AWS ALB/NLB) эффективен для веб-трафика (HTTP/TCP), но **категорически неприемлем для игровых серверов (сетевой код на базе Stateful UDP)**. 
> 
> Традиционный балансировщик выполняет трансляцию адресов (Source NAT) или терминирует сессию, выступая посредником. В результате игровой сервер «видит» IP-адрес балансировщика, а не реальный IP-адрес игрока. Это ломает логику игрового движка (счетчики пинга, гео-ориентированный подбор матчей/Matchmaking, защиту от читеров по IP и бан-системы). Более того, обработка сотен тысяч UDP-пакетов с состоянием в секунду на L7-прокси создает критический Latency-Overhead и Jitter.
> 
> В реальном производстве эта задача разделяется:
> * **Для HTTP/TCP (Авторизация, Магазин, Лобби):** Балансировщики используются. В RU-регионе разворачиваются высокопроизводительные комплексы на базе **DPDK** (Яндекс.Балансировщик), в EU-регионе — инстансы за AWS NLB или Cloudflare Spectrum.
